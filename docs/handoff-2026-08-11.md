## Community: ownership, likes, and “Create it”

Commit: `b4080195 Secure community creations and enable recreation`

- `POST /api/creations` now requires authentication and accepts only a
  published, generated recipe that belongs to the caller. The server derives
  the post name, author, goal, ingredient list, story, and image from that
  recipe; clients can no longer impersonate an author or publish an arbitrary
  ingredient list.
- Likes are durable account reactions, not `localStorage`. The schema adds
  `creation_likes` with a unique `(creation_id, user_id)` constraint. Like and
  unlike routes require auth, are idempotent, and adjust the counter only when
  a reaction actually changes.
- Community reads attach `likedByMe` for the signed-in account. The web client
  performs an optimistic update and rolls it back if the request fails.
- A community card exposes `Create it` on desktop hover/focus and always on
  small screens. It only appears when the post has a linked recipe.
- `/builder?recipe=<id>` now loads that exact public recipe and sends it through
  the normal allergy scan → recipe steps → log flow. It does not silently build
  a substitute. An active goal is still required, consistent with the rest of
  the Builder.
- Legacy seeded posts without a real recipe keep displaying, but deliberately
  say that recipe details are unavailable instead of offering a dead action.

## Public recipe provenance and copy safety

Commits:

- `918239b0 Clarify public recipe sources and ingredient catalog`
- `9b3f566a Sanitize public recipe copy`

- The recipe catalogue is now titled **Public Recipes**, not “Official
  Recipes.” Cards distinguish **Kitchen recipe** (curated) from **Built by a
  member** (a published builder result). This avoids claiming certification
  where a recipe is simply publicly shared.
- Public recipe search now covers recipe name, description, goal tags, and
  ingredient names.
- `artifacts/api-server/src/routes/recipes.ts` presents existing public data
  defensively: old curated marketing copy is replaced with neutral ingredient
  copy, and public member descriptions pass through the existing health-claim
  sentence filter. Private drafts remain unchanged for their owner.
- Recipe edits reject health-claim names and sanitize claim-bearing sentences
  from descriptions before a recipe can be published to the community.
- This uses the existing `features/naming` claim filter; do not bypass it by
  adding another free-form public-copy route.

## Ingredient glossary

Commit: `918239b0`

- The API now applies `features/catalog/presentation.ts` to every ingredient.
  It creates one English, consistent description format from the item’s
  category, Builder slot, flavour profile, and catalog highlights.
- Common ingredients use existing Unsplash food imagery. Each remaining item
  receives a colour- and ingredient-derived gradient, so there is no empty
  “missing image” card. The web image hides itself on load error and exposes
  that same gradient instead.
- The ingredients page no longer displays the inconsistent old description or
  Korean-name line. It keeps the Builder goal tags but labels them as goals,
  not medical benefits.
- The presentation layer is intentional: it updates established databases at
  response time. Editing seed text alone would not change databases that were
  seeded previously.

## Membership positioning

Commit: `60cdba3e Make memberships optional fulfillment plans`

- Core product access is explicitly free: Builder, recipe browsing, saving,
  publishing, and community do not require a plan.
- The still-unconnected checkout is intentionally left as a preview template.
  Its button asks for availability rather than pretending to charge a user.
- Paid options now describe real-world fulfilment rather than app feature
  gating:
  - **Ingredient Delivery** — two chilled/pre-portioned kits monthly, delivery
    scheduling and skips, limited to supported areas.
  - **Pickup Pass** — four made-to-order smoothie pickup credits at
    participating locations, with time windows and substitution confirmation.
  - **Blend & Pickup** — delivery plus pickup credits and fulfilment support.
- The formerly inert Community Wall link now navigates to `/community`.

## Weekly planning follow-up

Commit: `6492dd2c Improve weekly shelf planning flow`

- **Use instead** choices are now buttons, not decorative chips. Choosing one
  persists it against the skipped ingredient for the current week.
- The API validates that a selected substitute is still a safe, same-slot
  substitute for the signed-in user. The generation profile then prefers that
  substitute in its slot. It never bypasses allergy or other safety filters.
- The replacement area has an explicit **Skip without a substitute** action,
  so declining an ingredient does not force a swap.
- Settling a first weekly plan now remains on the week tab. Previously the app
  moved to Today immediately, making it feel as though the person had to click
  again to see the ingredients they had just requested.
- Planning has a short stage-by-stage reveal, and the final shelf cards enter
  in sequence. This makes the computation legible without claiming that an
  unfinished request has already completed.

## Local build support

Commit: `1308e0ee Support local native build dependencies`

- `pnpm-workspace.yaml` no longer excludes the native binaries required on
  macOS and Apple Silicon Docker (esbuild, Rollup, Lightning CSS, Tailwind
  Oxide). The prior Replit-only exclusions prevented Vite, the API build, and
  Drizzle from starting after a fresh local install.
- `allowBuilds.esbuild` is explicitly enabled; the former placeholder value
  was invalid under current pnpm and omitted esbuild's required binary.
- For this local session the latest services are available at
  `http://localhost:5174` (web) and `http://localhost:5002` (API). The older
  Docker dev ports may still serve the previous long-running containers until
  those containers are rebuilt.
